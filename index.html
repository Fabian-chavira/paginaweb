Protección y seguridad

6.1

Concepto y objetivos de protección y seguridad

La seguridad es el problema completo: impedir que personas no autorizadas lean, modifiquen o dejen sin servicio la información y los recursos de un sistema. La protección es el conjunto de mecanismos concretos del sistema operativo que se usan para resguardar esa información.

Objetivos de la seguridad

Cada objetivo tiene una amenaza asociada
ObjetivoQué garantizaAmenaza
ConfidencialidadSolo las personas autorizadas pueden leer los datos.Exposición de datos
IntegridadNadie puede modificar los datos sin autorización.Alteración de datos
DisponibilidadEl sistema responde cuando los usuarios legítimos lo necesitan.Negación de servicio

¿Quién ataca? Tipos de intrusos

Nivel 1

Curiosos casuales

Usuarios sin conocimientos técnicos que husmean en archivos que no les corresponden.

Nivel 2

Husmeadores internos

Personas de la propia organización que consideran un reto leer información ajena.

Nivel 3

Intentos decididos de lucro

Quienes buscan dinero: robo de datos bancarios, fraudes, venta de información.

Nivel 4

Espionaje comercial o militar

Ataques planeados y con muchos recursos contra información estratégica.

No todo es un ataque: pérdida accidental de datos

  • Desastres naturales: incendios, inundaciones, terremotos.
  • Errores de hardware o software: fallas de disco, cortes de energía, errores de programas.
  • Errores humanos: borrar un archivo por equivocación, montar el disco equivocado.

La defensa principal contra estos tres casos son los respaldos mantenidos en otro lugar.

Principio guía

Mínimo privilegio

Cada usuario y cada programa debe tener solo los permisos necesarios para su tarea, y ninguno más. Así, si algo falla o es atacado, el daño queda limitado.

En el libro (Tanenbaum, 2009): sección 9.1 «El entorno de seguridad», p. 613; 9.1.2 «Intrusos», p. 615; 9.1.3 «Pérdida accidental de datos», p. 616; 9.3 «Mecanismos de protección», p. 622.

6.2

Clasificación aplicada a la seguridad

Clasificar es asignar a cada usuario y a cada dato un nivel de seguridad, y decidir qué se puede leer o escribir comparando esos niveles. Es la base de la seguridad multinivel, usada sobre todo en entornos militares y gubernamentales.

Nota sobre la fuente: el libro de Tanenbaum trata la seguridad multinivel y los modelos formales (secciones 9.3.6 y 9.3.7), pero no una «clasificación de sistemas» con ese nombre. La tabla de niveles de certificación de más abajo es un complemento de otra bibliografía (ver Fuentes).

Niveles de clasificación de la información

Un ejemplo típico ordena la información de menor a mayor sensibilidad: Sin clasificar → Confidencial → Secreto → Ultrasecreto. Cada persona recibe una «autorización» (nivel) y cada documento una clasificación.

Confidencialidad

Modelo Bell-LaPadula

No leer hacia arriba: un usuario no lee documentos de nivel superior al suyo.
No escribir hacia abajo: no puede copiar información de su nivel a un nivel inferior, porque la filtraría.

Integridad

Modelo Biba

No leer hacia abajo: no se toma información de fuentes menos confiables.
No escribir hacia arriba: un proceso poco confiable no puede alterar datos de mayor confianza.

Prueba los dos modelos

Elige el nivel del usuario, el nivel del documento y la operación. Verás qué decide cada modelo.

Sistemas confiables y canales encubiertos

  • La base de cómputo confiable (TCB) es el conjunto de hardware y software que debe funcionar correctamente para que se cumpla la política de seguridad. Cuanto más pequeña, más fácil de verificar.
  • Un canal encubierto es una forma de pasar información entre procesos usando algo que no fue diseñado para comunicar (por ejemplo, el tiempo de uso del procesador), saltándose las reglas del sistema.

6.3

Funciones del sistema de protección

El sistema de protección responde a una pregunta constante: ¿este usuario o proceso puede hacer esta operación sobre este recurso? Para ello cumple varias funciones.

Función 1

Identificar y autenticar

Comprobar quién es el usuario antes de darle acceso (contraseñas, tarjetas, biometría; ver 6.6).

Función 2

Autorizar el acceso

Decidir qué operaciones puede hacer cada sujeto sobre cada objeto, usando dominios y matrices de acceso (ver 6.4).

Función 3

Aislar procesos y memoria

El hardware distingue el modo kernel del modo usuario y da a cada proceso su propio espacio de direcciones, para que no se interfieran.

Función 4

Proteger archivos y dispositivos

Archivos y dispositivos de E/S aparecen en el sistema de archivos como objetos con nombre, así que se les aplican las mismas reglas de permisos.

Función 5

Separar política y mecanismo

El mecanismo es cómo se hace cumplir la regla; la política es qué regla se aplica. Separarlos permite cambiar las reglas sin reescribir el sistema.

Función 6

Registrar y auditar

Guardar bitácoras de accesos e intentos fallidos para detectar abusos y revisar qué ocurrió.

Ejemplo real: permisos de archivo en UNIX y Linux

Cada archivo guarda tres grupos de permisos: para el propietario, para su grupo y para los demás. Cada grupo puede tener lectura (r), escritura (w) y ejecución (x).

-rwxr-x---  1  ana  equipo  informe.sh
 │└┬┘└┬┘└┬┘
 │ │  │  └─ otros:        sin permisos
 │ │  └──── grupo:         leer y ejecutar
 │ └─────── propietario:   leer, escribir y ejecutar
 └───────── tipo de archivo (- = archivo normal)

En el libro (Tanenbaum, 2009): cap. 1, p. 1 (modo kernel y modo usuario); 5.3.3, p. 355 (los dispositivos como objetos con nombre y protegidos como archivos); 9.3 «Mecanismos de protección», p. 622; 9.4 «Autenticación», p. 641.

6.4

Implantación de matrices de acceso

Un dominio es un conjunto de pares (objeto, derechos): dice qué se puede hacer con cada objeto. Cada proceso se ejecuta dentro de un dominio (en UNIX, un dominio queda definido por el UID y el GID del usuario). Todos los dominios juntos forman la matriz de acceso.

  • Filas: los dominios (usuarios, grupos o procesos).
  • Columnas: los objetos (archivos, impresoras, memoria…).
  • Cada celda: los derechos que el dominio tiene sobre ese objeto.

El problema de implantarla

Una matriz completa sería enorme y casi toda estaría vacía, así que no se guarda tal cual. Se almacena de dos formas:

Por columnas

Listas de control de acceso (ACL)

Cada objeto lleva la lista de quién puede hacer qué con él. Se revisa al abrir el objeto. Es fácil quitar el permiso de alguien. Los permisos de UNIX son una versión corta de este esquema.

Por filas

Capacidades

Cada dominio guarda una lista de «llaves» que indican a qué objetos puede acceder y con qué derechos. Se pueden pasar a otro proceso, pero deben protegerse contra falsificación y es más difícil revocarlas.

6.5

Protección basada en el lenguaje

En vez de depender solo del núcleo del sistema operativo, parte de la protección se puede expresar en el lenguaje de programación: el compilador y el entorno de ejecución comprueban qué puede hacer cada pieza de código.

Nota sobre la fuente: el libro de Tanenbaum no tiene una sección con este nombre. Lo más cercano es el encapsulamiento de código móvil y la seguridad de Java (9.8.6 y 9.8.7). El resto del tema es un complemento de otra bibliografía (ver Fuentes).

Ideas principales

Tipos

Seguridad de tipos

El lenguaje impide usar un dato de una forma no permitida, por ejemplo tratar un entero como si fuera una dirección de memoria o escribir fuera de los límites de un arreglo.

Encapsulamiento

Datos privados

Con private y public, una clase decide qué partes de sus datos puede tocar el resto del programa.

Verificación

Antes y durante la ejecución

Muchas reglas se comprueban al compilar o al cargar el programa, así que se evita parte del costo de vigilar cada acceso en tiempo de ejecución.

Declarativa

La política en el código

El programador declara qué recursos puede usar un componente, y el sistema se encarga de hacerlo cumplir.

El caso de Java

  • Java se compila a bytecode, que la máquina virtual (JVM) ejecuta.
  • Antes de ejecutar una clase, el verificador de bytecode comprueba que respete los tipos y que no haga operaciones peligrosas con la pila.
  • El código descargado (como los antiguos applets) corría en un entorno restringido o sandbox, con permisos limitados según su origen o su firma.
  • El Security Manager, que aplicaba esas políticas, fue declarado obsoleto y retirado en versiones recientes de Java. Hoy el aislamiento suele delegarse en el sistema operativo y en contenedores.

Ejemplos actuales

Rust evita en tiempo de compilación muchos errores de memoria que en C causan vulnerabilidades. Los navegadores ejecutan el JavaScript de cada página en un entorno aislado con acceso limitado al equipo.

Protección del sistema operativoProtección del lenguaje

6.6

Validación y amenazas al sistema

La validación (autenticación) comprueba que quien pide acceso es quien dice ser. Las amenazas son los intentos de saltarse esa protección o de aprovechar errores del software.

Validación: ¿quién eres?
Algo que sabes

Contraseñas

El sistema no guarda la contraseña, sino su hash (con «sal» agregada). Los ataques típicos son adivinarla o probar un diccionario de palabras comunes.

Algo que tienes

Objeto físico

Tarjeta con chip o banda magnética, llave USB o token. Se puede perder o robar, por eso suele combinarse con un PIN.

Algo que eres

Biometría

Huella, iris o rostro. Puede equivocarse: rechazar a la persona correcta o aceptar a la equivocada.

Usar dos o más de estas categorías juntas (autenticación de dos factores) hace mucho más difícil suplantar a alguien.

Ataques desde el interior
Bomba lógica

Código dormido

Programa escondido que se activa cuando se cumple una condición, por ejemplo cuando un empleado deja de aparecer en la nómina.

Trampa

Puerta trasera

Entrada secreta que un programador deja en el sistema para saltarse la autenticación normal.

Suplantación

Falso inicio de sesión

Pantalla de acceso falsa que captura el nombre y la contraseña del usuario que cree estar entrando al sistema.

Explotación de errores en el código
Desbordamiento de búfer

Escribir de más

Se mandan más datos de los que caben en un arreglo y se sobrescribe la memoria vecina, por ejemplo la dirección de retorno de una función.

Cadena de formato

Entrada como formato

Si un programa usa texto del usuario como cadena de formato de printf, el atacante puede leer o escribir en memoria.

Retorno a libc

Reusar código existente

En lugar de inyectar código propio, el atacante desvía la ejecución hacia funciones que ya existen en la biblioteca del sistema.

Desbordamiento de enteros

Cuentas que se pasan

Una operación excede el rango del entero y da un resultado inesperado, por ejemplo un tamaño de memoria demasiado pequeño.

Inyección de código

Entrada sin validar

Se cuelan comandos (de shell, de SQL) dentro de datos que el programa acepta sin revisar.

Escalada de privilegios

Ganar más permisos

Aprovechar un fallo para pasar de usuario normal a administrador (root).

Malware
Troyano

Parece útil

Programa que aparenta hacer algo legítimo, pero esconde código malicioso. El usuario lo instala voluntariamente.

Virus

Se adhiere y se copia

Se inserta en otros programas y se replica cuando el programa infectado se ejecuta. Necesita un anfitrión.

Gusano

Se propaga solo

Se copia a sí mismo por la red sin necesitar un programa anfitrión, aprovechando fallos de otros equipos.

Spyware

Espía

Reúne información del usuario (sitios visitados, datos escritos) y la envía sin que él lo sepa.

Rootkit

Se esconde

Conjunto de herramientas que oculta la presencia del intruso y le mantiene acceso privilegiado al sistema.

Defensas
Red

Firewall

Filtra el tráfico entre redes según reglas: deja pasar lo permitido y bloquea el resto.

Detección

Antivirus

Busca malware por firmas conocidas y por comportamiento sospechoso, y lo elimina o aísla.

Origen

Firma de código

El software lleva una firma digital que permite comprobar quién lo publicó y que no fue alterado.

Aislamiento

Encarcelamiento

Un programa se ejecuta en un entorno restringido (como chroot) donde solo ve una parte del sistema.

Vigilancia

Detección de intrusos

Vigila el comportamiento del sistema y avisa cuando algo se desvía de lo normal.

Código móvil

Encapsulamiento

El código descargado (scripts, applets) se ejecuta en un entorno aislado con permisos limitados.

En el libro (Tanenbaum, 2009): 9.4 «Autenticación», p. 641; 9.5 «Ataques desde el interior», p. 656; 9.6 «Cómo explotar los errores en el código», p. 659; 9.7 «Malware», p. 667; 9.8 «Defensas», p. 692.

6.7

Cifrado

Cifrar es transformar un mensaje legible (texto plano) en uno ilegible (texto cifrado) usando un algoritmo y una clave. Solo quien tenga la clave correcta puede volver a leerlo.

Una regla básica (principio de Kerckhoffs): la seguridad debe depender del secreto de la clave, no de ocultar el algoritmo, que puede ser público y revisado por expertos.

Tipos de cifrado

Una sola clave

Clave secreta (simétrica)

La misma clave cifra y descifra. Es rápida, pero ambos extremos deben compartir la clave sin que nadie más la conozca. Ejemplo actual: AES. DES ya es obsoleto.

Dos claves

Clave pública (asimétrica)

Cada persona tiene una clave pública (se reparte) y una privada (se guarda). Lo cifrado con una solo se descifra con la otra. Ejemplo: RSA. Es más lenta.

Sin vuelta atrás

Funciones de una vía

Es fácil calcular el resultado, pero prácticamente imposible recuperar la entrada. Se usan los hash (como SHA-256) para guardar contraseñas y comprobar integridad.

Autenticidad

Firmas digitales

Se calcula el hash del documento y se cifra con la clave privada del firmante. Cualquiera lo verifica con la clave pública: prueba quién firmó y que no se alteró.

Módulo de plataforma confiable (TPM): chip de la placa base que guarda claves de cifrado y ayuda a comprobar que el equipo arrancó sin modificaciones.
